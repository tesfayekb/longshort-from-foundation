Investigation surfaced TWO distinct problems:

**P1 (INC-70 — data correctness, severity HIGH).** A 9-variant probe of `/stocks/filings/vX/form-4` against the deployed `POLYGON_API_KEY` returned **byte-identical 1.85 MB / 1000-row firehose responses** for: single-ticker, `ticker.any_of`, comma-list, `ticker.in`, pipe-delimited, repeated-param, market-wide 90-day, AND market-wide 14-day. `ticker=AAPL` returned rows NOT containing AAPL (top buckets: DELL=312, FCNCA=41, SSMR=38). Only `limit=` was honored. The endpoint silently ignores `ticker` (every syntax) AND `transaction_date.*` — Candidates A (multi-ticker), B (date-chunked), C (per-ticker) are ALL impossible at this entitlement tier. The original FP-042 per-ticker fetcher was therefore broken since deploy: it fetched the same firehose 839×, locally filtered by `tickers[0]===ticker` (would yield ~0 rows per name since our universe isn't dominant in the firehose), and the compute layer marked each ticker `no_qualifying_transactions` — perfectly indistinguishable from the EXPECTED sparse profile. **Phantom signal: looked sparse, was actually wrong.** The ACT-155 CPU failure was the lucky trigger that exposed the silent data bug.

**P2 (telemetry double-tally).** The ACT-155 catch block pushed 839 per-ticker `fetch_error` skips on a market-wide throw, then assigned `marketWide = { kind:'rows', rowsByTicker: new Map() }` WITHOUT returning, falling through into the qualifying-filter loop which pushed 839 MORE `no_qualifying_transactions` skips. Two skip classes per ticker, 1678 total — telemetrically impossible.

**This addendum's scope.** (a) **`insider-orchestrator.ts`** — the market-wide-throw catch block now returns `outcome='failed'` with `failure_reason='form4 market-wide fetch failed: <thrown message>'` and `skipped: []`, short-circuiting before the qualifying-filter loop. A run can never again show two skip classes for the same ticker. The `kind:'unavailable'` branch (typed entitlement state — 403/404 — neither a throw nor a fetcher error) is UNCHANGED. (c) **FP-042 compute / classifier / filter / z-score code is UNTOUCHED** — it is correct and reused as-is when the EDGAR fetcher lands (DW-094). Only the data-acquisition layer needs replacing. (d) **Docs** — INC-70, DW-094, this addendum, ACT-156, `insider-transactions.md` ACT-156 addendum, NEW `_pattern-vendor-fetcher-filter-honesty.md`.

**Pattern lesson (codified, applies to remaining feed-signals).** Every vendor-endpoint fetcher MUST implement a `verifyFilterHonored()` pre-flight: probe with a filter value that SHOULD return zero rows (e.g. `ticker=ZZZZZZZZ`, far-future date) and assert the response is empty — NOT a firehose. If a should-be-empty query returns data, the filter is silently ignored and client-side filtering will produce wrong data. This would have caught INC-70 on day one. Bound as a §22.3-style pre-flight item for Signals #1 (analyst), #2 (PEAD), #3 (options), #8 (news) — each has its own vendor endpoint whose filters must be probed before trust.
